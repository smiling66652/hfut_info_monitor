# 密钥轮换与历史清理指南

> ⚠️ 本文档**只含键名与轮换入口，不含任何真实密钥值**。所有应填入的值一律用 `<新XXX>` 形式的占位符表示。
> 本文件本身要进仓库，写进真实值等于二次泄露，请务必保持占位符。

---

## 第一部分：必须轮换的密钥清单

以下键名取自 `config/config.json` 的真实结构。轮换后，把新值填入 `config/config.json` 对应路径即可（该文件已被 `.gitignore` 忽略，本地保留、不会入库）。

### 补充说明（不是密钥、无需轮换的项）

- **`ima.kb_id`（IMA 知识库 ID）**：这是知识库的**标识符**，不是密钥，不能用于鉴权。泄露不会带来认证风险；而且改了它会让程序找不到原有知识库。**因此不用轮换**，保持原值即可。
- **个人身份标识（PII）**：`qq_accounts[].qq`、`qzone.login_qq`、`napcat.bot_qq`、`push_method.sender_email` / `receiver_email` 等是 QQ 号 / 邮箱地址，属于账号标识，不是可「重置」的密钥，无法像密码那样轮换。若在意隐私可手动脱敏，但不纳入本轮换表。
- **登录态 cookie**：`data/qzone_cookies.json`、`data/qzone_feed_cookies.json` 位于已被 gitignore 的 `data/` 目录，不入库。若担心泄露，重新扫码登录 QQ 空间即可使旧 cookie 失效，无需「轮换」。

## 第二部分：历史清理方案对比

> 含密钥的文件 `config/config.json` 残留在 3 个历史提交中：`89a0dc6`（Initial commit）、`66b7ab3`（Upload config/config.json）、`fde08f3`（v2.0 升级）。最新提交 `e4d5100` 已将其从工作树删除。

### 方案 A：不清理历史，只轮换密钥

- **命令**：无（仅执行第一部分的密钥轮换）。
- **会发生什么**：Git 历史里那 3 个旧提交仍能翻到旧密钥文本，但**旧密钥已轮换失效，无法再用于认证**，实际无害。
- **代价**：零。无需 force push，协作者无感，仓库历史原样保留。
- **注意**：若某个密钥因故**无法轮换**（如对应账号已无法登录），则该旧值仍然有效，此时方案 A 不成立，必须选 B/C。

### 方案 B：git filter-repo 彻底清除

**前置（重要）**
- 先整目录备份：在文件资源管理器复制 `hfut_info_monitor` 为 `hfut_info_monitor.bak`，或
  ```bat
  xcopy /E /I hfut_info_monitor hfut_info_monitor.bak
  ```
- 保证工作区干净：把未提交改动（`scripts/` 下 5 个 `.py`、`.env.example` 及一批 untracked 文件）先 `git commit` 或 `git stash`，避免改写历史时弄乱。
- 安装（Windows，需 Python）：`pip install git-filter-repo`；或到 https://github.com/newren/git-filter-repo/releases 下载。

**具体命令（在仓库根目录执行）**
```bat
git filter-repo --path config/config.json --invert-paths --force
```
- 说明：`--force` 是因为当前不是全新 clone；filter-repo 出于安全会自动**移除 `origin` 远端**，并在 `.git/filter-repo/` 留备份映射。

**重新关联远端并强推**
```bat
git remote add origin https://github.com/smiling66652/hfut_info_monitor.git
git push --force --all
git push --force --tags
```

- **会发生什么**：`config/config.json` 从全部历史提交中抹除（含 `89a0dc6`/`66b7ab3`/`fde08f3`），所有受影响的 commit hash 改变。
- **代价**：
  - 必须 `git push --force`，普通 push 会被拒绝（**这一不可逆动作必须由你本人确认**）。
  - 任何已 clone / fork 的协作者必须删除旧仓库重新 clone，否则会把含旧密钥的历史又推回。
  - 已有的 fork、PR、Issue 附件副本不会被自动清除；GitHub 缓存中可能短期残留旧内容。
  - CI/CD、webhook、部署密钥若写死旧 commit hash 会失效。
  - ⚠️ 仍建议**同时轮换密钥**（见第一部分）：历史可能已被他人 clone / 缓存过，仅靠改写历史不能 100% 保证密钥未泄露。

### 方案 C：BFG Repo-Cleaner

**前置**：需要 Java 运行环境。先确认：
```bat
java -version
```
无则先安装 JDK / Java 11+，再到 https://rtyley.github.io/bfg-repo-cleaner/ 下载 `bfg.jar`。

**具体命令（在仓库的父目录执行）**
```bat
java -jar bfg.jar --delete-files config.json hfut_info_monitor
cd hfut_info_monitor
git reflog expire --expire=now --all
git gc --prune=now
git push --force --all
```
- 说明：BFG 默认**不改动最新提交**中的文件；本仓库最新提交 `e4d5100` 已删除 `config/config.json`，符合条件。BFG **不会**移除 `origin` 远端。
- **会发生什么**：与方案 B 相同——`config/config.json` 从历史抹除、commit hash 全变。
- **代价**：同方案 B（需 force push、协作者重 clone、fork / 缓存残留）。
- **与 B 的对比**：BFG 通常更快、命令更短；`git filter-repo` 是 Git 官方推荐、更灵活（可按路径精细控制、替换文件内文本）。二者清理效果等价，选哪个都行。

## 第三部分：推荐路径

**结论（明确推荐）：默认采用方案 A —— 只轮换密钥、不清理历史。**

理由：
1. 本仓库是**个人项目，唯一 contributor**，没有协作者需要重 clone，也没有公开 fork；方案 B/C 的主要代价（force push、hash 全变、协作中断）在这里没有对应的收益。
2. **密钥轮换后旧值立即失效**，留在历史里的明文只是「已死」的字符串，没有实际利用价值。真正「止血」靠第一部分，而不是改写历史。
3. 历史清理的溢价在于「洁癖 / 公开审计」，而非「安全止血」；对本项目性价比为 0。

**何时升级到方案 B/C（触发条件）**
- 你打算把这个仓库**公开**（作为保研作品集对外展示），介意历史里残留明文；
- 或某个密钥因账号原因**无法轮换**，旧值仍有效，必须靠改写历史清除；
- 或你有强洁癖、希望提交历史 100% 干净。

**执行顺序建议**
1. 无论选哪条路，**先完成第一部分密钥轮换**——这是真正止血的动作，立即做。
2. 历史清理属于可选项，等你确认后再决定是否 force push；在决定前**不要 push**。

> 备注：本指南、密钥轮换、本次安全修复提交（`e4d5100`）都就位后，若要把相关文件正式入库，请单独提交；在历史清理方案确定前不要执行 `git push --force`。
