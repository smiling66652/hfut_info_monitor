二已实现功能的优化方向（代码级审计）

以下为对 hfut_site/ 与 scripts/ 逐文件审计结果，每条附 file:line，供直接落地。既有文档未覆盖此层。

2.1 数据安全：无内容哈希兜底 + 索引静默重置 P0

hfut_scanner.py:1820-1821 的新增判定仅基于 normalize_url(url)（item_key 见 :175-197，只归一化协议/主机/端口/斜杠/fragment，不含 title/date/正文）。而 load_index()（:1776-1780）无任何 try/except：一旦 hfut_full_index.json 损坏/被清空，立即静默重置为 []。

事故场景：索引损坏 → 全部历史 URL 判定为"新增" → 海量重复推送轰炸 30 人。当前无任何内容哈希作兜底。这是最该先修的可靠性黑洞。
  • 新增内容指纹：对每条持久化 content_hash(url+title+date)（hashlib 已在 :28 导入却从未用于 diff）；
  • load_index/load_state/load_failed_sites 统一包 safe_load_json(path, default)，损坏时告警并保留上次快照，绝不静默 []；
  • 建独立"已推送 URL 集合"去重表，与索引解耦。

2.2 变更检测停留在 URL 级 P0

系统是列表页增量扫描：URL 新出现才算"新增"。但大量高价值动作发生在已存在通知的更新——招生简章补报名、截止日期顺延、附件 PDF 替换、名单公示更正。这些当前完全不可见。

  • 对已进入索引的重点通知（保研/竞赛/招生/中标类），周期性抓取详情页正文做 hash/语义 diff；
  • 哈希变化 → 标记"已更新"并推送变更摘要（与 3.1 共用正文抓取底座）；
  • 补逐条历史快照（按 URL 存 N 个版本），支持"上周这通知长什么样"回看。

2.3 三套分类体系重复且矛盾 P1

分类逻辑被三处重复实现，且口径互相打架：

  • hfut_config.classify_hfut()（:61-77，中文类目，含"教务"）；
  • hfut_scanner.score_item + categorize_item（:1387-1408，英文类目，无"教务"）；
  • HIGH_PRIORITY_KEYWORDS / RELATED_KEYWORDS（:396-433，独立关键词表）。

后果：索引存英文 category，邮件/CLI 又用 classify_hfut() 按中文重分类，"教务"通知在索引里是 other、在邮件里却标"教务"，每日摘要按英文分组 → 教务落入"其他"桶。建议只保留一套权威分类（推荐 hfut_config 为权威），索引存中文类目，报告直接读索引，删掉 categorize_item。

2.4 多通道未接入主链路 + 无跨账号 failover P1

hfut_notify.py（apprise 200+ 渠道）是孤儿模块（见 1 节）。hfut_email.send_email()（:348-401）仅做同账号 465→587 降级，无"主账号失败切备用账号"、无"切企微/钉钉"。一旦 SMTP 授权码失效，整条推送链静默全挂。

  • 在 send_email_report() 成功/失败后调用 hfut_notify.push() 作备用通道，或做成策略链（SMTP 失败 → apprise）；
  • 支持主/备 SMTP 账号、多收件人组，任一路成功即返回。

2.5 状态文件读取无异常保护 P1

load_index()（:1776）、load_state()（:1766）、load_failed_sites()（:902）均无 try/except，而 save_scan_log（:1742）反而有——不一致。统一 safe_load_json()（与 2.1 同改）。

2.6 _url_cache 跨线程无锁 P1

_url_cache 定义于 :119，被 fetch()（:535）与 fetch_requests_bs4()（:578）多线程并发读写（ThreadPoolExecutor(max_workers=6)，:1906）。数据竞争风险。改用 threading.Lock 包裹，或直接用 functools.lru_cache/requests 自带缓存。

2.7 巨型单体 + print 调试 + 无日志框架 P1

hfut_scanner.py 2073 行混合抓取/解析/评分/IO/HTML 生成/编排，全程 print（:386,567,661…）。建议拆分为 fetcher / parser / classifier / state / report 子模块；引入 logging 分级（DEBUG/INFO/WARN/ERROR），CLI 摘要与日志分离。

2.8 硬编码绝对路径/密钥 P2

_NODE_EXE（:665，写死 C:\Users\Matebook\.workbuddy\binaries\node\...）、Edge 路径（:708-710）。改环境变量 / shutil.which("node") 优先，探测失败给可读错误。可移植性与换机部署直接相关（比赛演示常换环境）。

2.9 收件人邮箱硬编码于源码 P2

hfut_email.py 中 5 个真实 QQ 号重复出现于 :13 / :422 / :499 等多处。仅保留在 hfut_email_config.json，源码/文档用占位符。

2.10 重复代码块 P2

_try_smtp 在 _send_plain_email 与 send_email 各定义一次（:319-335 / :370-386）；extract_items_standard 与 extract_items_news_cms 近逐行相同（:913-958）；_ensure_utf8_console 在 4 个文件各抄一份（注释自认 :69）。抽取公共工具模块。

2.11 索引无上限增长 P2

existing_index.extend(...) 后整文件写回（:1986-1988），无归档/裁剪 → hfut_full_index.json 已 328KB 且持续膨胀。保留近 N 天或按 URL 去重后限长，冷数据归档。

2.12 TLS 全局关闭 P2

SSL_CTX.verify_mode = ssl.CERT_NONE（:91）；requests verify=False（:597）。对已知内网证书链问题站点白名单放行，其余恢复校验（安全与合规前置，呼应商业化报告）。

2.13 new_count 口径不一致 P2

CLI 用 len(index)-count_before（URL 级，:256）；邮件用 date == today（日期级，:158）。二者可能不符，"今日新增 N 条"数字与列表对不上。统一以"本扫描周期新增 URL 集合"为准。

2.14 HTML 注入 / 转义缺失 P2

build_html_report() 标题/URL 直接 f-string 注入（:126-147），仅摘要页转义。所有用户可控字段统一 html.escape，防排版破损（标题含 & 等已实测会断行）。

2.15 死代码 / 冗余模块清理清单 P2

下述模块经 grep 确认零 import（仅自身引用）或未接入主流程，属可删/可合并（详见附录）：main.py(1174)、qq_group_scraper.py(1405)、qzone_scraper.py(1249)、wechat_article_scraper.py(1189)、wechat_monitor_enhanced.py(241)、notion_manager.py(475,已禁用)、data_sync.py(436)、storage_manager.py(594)、fault_tolerance.py(711)、ocr_extractor.py(937)、playwright_scraper.py(625)、qq_group_collector.py(623)。清理后仓库体积与认知负担大幅下降。

2.16 smart_digest 与 daily_digest_v2 重复触发 P1

二者都在 all 模式触发（task_orchestrator 与 run_all_mode 收尾），功能高度重叠，存在重复发信风险。二选一作为唯一摘要入口，或明确分工（一个即时、一个每日）。

2.17 wechat_monitor 已弃用但仍被触发 P2

文件头标 DEPRECATED，却被 ai_secretary.run_secretary() 兜底分支在运行时触发 → 微信被弃用模块重复采集。建议从主流程去掉该兜底或直接删除 wechat_monitor，统一走 wechat_account_monitor。

2.18 每日情报子系统未接入自动流水线 P1

opportunity_pick / competition_calendar / send_daily_intel / daily_intel_template / manage_recipients 能独立跑，但没挂进 main_controller 自动每日流水线。若这是当前主推产品，应接入 task_orchestrator 取代/整合旧 smart_digest 路线，保证"到时自动发"。

2.19 测试覆盖缺口 P2

纯函数单测较全（normalize_url/score_item/extract_*/generate_daily_summary 等约 60 用例）；但未覆盖：① 网络抓取 fetch/fetch_with_fallback；② 扫描编排 diff/去重/并发；③ load_index 损坏恢复；④ build_html_report；⑤ _url_cache 线程安全；⑥ 内容变更检测（当前不存在）。补"索引损坏→不重推"与"同 URL 内容变更→标更新"两条回归用例，直接护住 2.1/2.2。

三可扩展新功能（产品维度）

本节约等于既有《功能扩展与优化调研》的"新功能"部分，但补充了具体借鉴技术（与第四章对标呼应）。优先级与排期见第五章。

3.1 内容级变更检测（最高新增价值）P1

借用监控最佳实践：①MD5 短路——抓完先算 MD5 与上次比对，一样直接跳过解析（省 ~90% 无效处理，约 20 行改动）；②DOM 降噪——比对前清洗动态类名/CSRF Token/时间戳（业界用 AST 级清洗把误报率从 95% 降到个位数）；③段落级 diff + ignore_junk——只比对正文容器，忽略计数器/广告轮播；④差异摘要——用 difflib 生成人读 unified_diff 或让 LLM 改写"截止日期由 X 改为 Y"。

3.2 语义级去重（最高性价比）P0

现状只 normalize_url() 合并同链接。两阶段去重（业界标准）：先标题指纹（Jaccard/SimHash）快速过滤，再轻量 embedding（bge-small-zh/all-MiniLM，本地零成本）对近 48h 窗口做余弦相似度 ≥0.82 判重。滚动窗口避免"同届赛事每年重发"被误杀；合并时保留研究生院/校主页等权威源。

3.3 详情页结构化抽取 + DDL 倒计时 P1

对高相关条目抓详情页正文，LLM 做 schema 校验抽取：deadline / object / action_required / contact / one_line_why。抽取与推理分离（deadline 只取原文，缺失填 null）。抽出的 deadline 直接喂 competition_calendar.py 的"还有 N 天"逻辑——学生最痛的"错过 DDL"点，已被竞品（保研机构）验证为付费意愿最强的功能。

3.4 个性化订阅（比赛差异化核心）P0

现状 30 人收完全相同邮件。每位收件人维护兴趣标签（保研/竞赛/就业/学术/奖学金），日报按标签生成不同子集投递；进阶做基于打开/点击行为的协同过滤。改动发送层、收益最直观。

3.5 实时/即时告警 + apprise 接入主链路 P1

现状仅每日 08:00 批处理。对"夏令营系统开放 / 报名今晚截止 / 突发保研政策"等时效性极强信息，扫描命中"高优先级+新鲜度极高+含临近 deadline"时立即经 apprise 推钉钉/企微/WxPusher/Telegram（手机推送打开率远高于邮件）。与日报互补不替代。先把孤儿模块 hfut_notify.py 接进 send_email_report()（改动小、立刻解锁微信推送）。

3.6 附件下载 + OCR 全文 P2

ocr_extractor.py 已就绪；自动下载 PDF/图片附件 OCR（本地 PaddleOCR 边际成本≈0，云端仅兜底），实现正文级全文检索，对招生简章/名单公示尤其有用。

3.7 RSS / API 对外暴露 P2

系统已是最全的合工大通知聚合源。对外 RSS/Atom 或 REST API，是产品化与商业化入口（canonical_url + sources + category + summary 结构）。

3.8 知识库 / RAG 问答激活 P2

IMA 已同步但没用起来：历史语义检索（"去年保研夏令营什么时候开始的？"）、对话式查询、日报加"相关历史"链接。

3.9 可视化 Web 仪表盘 P2

轻量仪表盘：栏目覆盖趋势、分类占比、30 天热力图、关键词云——既是运维工具，也是比赛"系统可视化"亮点。

3.10 图书馆第 37 栏目确定性修复 P0

唯一稳定失败栏目：lib.hfut.edu.cn React SPA 在无头 Edge 始终不挂载（连续两次返回 120KB noscript 兜底页）。优先修：CDP 用 wait_for_function 等 .dbTime 出现再取 HTML；不行则改抓 React 先发的 JSON 接口数据。小修补、补全覆盖盲区。

3.11 AI 层成本校准 P2

本地 Ollama/规则做"是否值得分析"廉价预判，仅高相关调云端；relevance 打分加"示例+周度抽检"防阈值漂移；本地缓存 embeddings/摘要避免重复调模型。

3.12 多校 / 多校区泛化 P2

栏目收敛在 CHANNELS 配置，可扩到安徽其他高校——参赛可作"通用高校情报中台"泛化论证（注意商业化报告指出跨校源库是纯人力活，需节奏控制）。

四外部最佳实践对标（changedetection.io 深挖）

通过联网调研（changedetection.io 官方/社区文档、WebSearch 2026-09-27）整理其能力矩阵，作为可借鉴的技术清单。该开源项目 32.5k★、Apache-2.0，是"通用监控引擎"的标杆——你的差异化不在重造它，而在"中国高校源库 + 教育语义"垂直层。

4.2 其"降噪与智能化"能力（比赛可对标的点）

  • 元素级监控：CSS/XPath/JSONPath/jq 选择器只盯正文容器，忽略导航/页脚噪声 → 你的"ignore_junk"思路；
  • Visual Selector：点哪监控哪 → 可降级为"用户从抓取结果勾选有效条目"覆盖 80% 需求；
  • Browser Steps：登录/填表/点按钮后再检测 → 你的 WebVPN/登录态采集可借用；
  • AI 变更过滤 + AI 摘要：用 LiteLLM 接任意模型，写自然语言意图（"仅在价格低于 ¥50 时通知"）过滤噪声，并把 raw diff 改写成"价格由 ¥89.99 降到 ¥67.00" → 你 3.1/3.3 的 LLM 改写可直接对标；
  • 85+ 通知渠道（Apprise）→ 你已有 hfut_notify.py 同款底座，只差接入主链路（2.4/3.5）；
  • per-watch 代理 / 条件触发 / 时区调度：规模化运营的成熟特性，标注为长远演进方向。

4.3 网页监控通用最佳实践（可落地的具体技巧）

  • MD5 短路：抓完先 hash，未变就跳过解析（省 90% 处理）；
  • DOM 降噪管道：比对前用 AST 级清洗去掉 Tailwind hash 类名、CSRF Token、轮播时间戳——纯字符串/MD5 比对的误报率高达 95%，降噪后个位数；
  • 双层检测架构：快速 HTTP 抓取 + 仅 JS 站走 Playwright，兼顾并发与成本（与你现有四级兜底同源思想）；
  • 像素 diff 调参：pixelmatch threshold 0.1 + 变化像素占比 0.1% 容差，过滤渲染抖动；
  • 内容截断：快照上限 5000 字符，防 DB 无限膨胀（呼应你 2.11 索引限长）；
  • 人读 diff：difflib.unified_diff 生成前后对比，通知带"变化了什么"而非"变了"。
借力而非重造：通用引擎（抓取/调度/diff/通知）changedetection.io 已做得极好且开源。你的护城河是它做不到的垂直层——高校栏目源库、教育语义分类、保研/竞赛 DDL 理解、学生个性化订阅。架构上可考虑"自研垂直层 + 可选借 changedetection 做通用底座"，而非从零写监控内核。
