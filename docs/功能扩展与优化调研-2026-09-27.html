一、调研结论速览

你的项目在「采集—解析—容错—推送」这条主链路上已经相当成熟：37 个官网栏目、三级抓取兜底（urllib→requests→CDP）、通用+专属双解析器互补、URL 归一化去重、发件账号自动降级、固定模板防漂移——这些在同类个人项目中属于第一梯队，已具备参赛展示的完整度。

但对照业界（changedetection.io、Visualping、AI Morning Briefing 流水线）和你的实际业务目标（保研/竞赛/就业人群），有明显四类缺口：① 内容级变更检测缺失（只检测"新 URL"，检测不到"旧通知被更新"）；② 去重只做 URL 级、未做语义级（同事件多院重复发、措辞改写仍算多条）；③ 推送是"一刀切广播"（30 人收到完全相同内容，未个性化）；④ 缺少实时/即时告警通道（仅每日批处理，保研夏令营开放、报名临近等时效性强的信息被稀释）。

一句话建议：现有系统已是「好用的工具」，下一步把它做成「懂你的情报产品」——补齐内容变更检测、语义去重、个性化订阅、实时告警四块，既是最高价值的工程扩展，也是最利于比赛答辩的差异化创新点。

三、已实现功能的优化方向（做精，不动大架构）

3.1 去重升级：URL 级 → 语义级（最高性价比）

现状只靠 normalize_url() 合并同链接。但合工大各学院经常把同一份通知（如校发文件、全校性竞赛）分别挂在多个站点、URL 不同，或同一事件改写标题重发，目前会被记为多条。

  • 两阶段去重（业界标准做法）：先词法（标题 Jaccard / 标题指纹）快速过滤明显重复，再语义（轻量 embedding 如 bge-small-zh / all-MiniLM，本地跑、零成本）对近 48 小时窗口做余弦相似度 ≥0.82 判重。
  • 滚动窗口：只对最近 N 条比对，避免"同一届赛事每年重发"被误杀。
  • 保留权威源：合并时优先保留研究生院/校主页等权威源，其余作为"同事件其他来源"列出。
  • 价值：直接降低日报噪声、提升"今日新增"可信度，也是比赛里能讲清的算法亮点。

3.2 内容级变更检测（最大新增价值）

现状是列表页增量扫描：新出现一个 URL 才算"新增"。但大量高价值信息发生在已存在通知的更新上——招生简章补报名、截止日期顺延、附件 PDF 替换、名单公示更正。这些目前完全看不到。

  • 对已进入索引的重点通知（保研/竞赛/招生/中标类），周期性抓取详情页正文做 hash/语义 diff，检测到实质性变化（非日期戳/广告轮播）时触发"更新提醒"。
  • 可借鉴 changedetection.io 的"元素级监控"思路：只比对正文容器，忽略导航/页脚噪声。
  • 此能力与"语义去重"共用 embedding/正文抓取基础设施，边际成本低。

3.3 详情页结构化抽取（让情报"说人话"）

现状只抓标题+日期+链接。日报里每条都是干巴巴的标题，缺少"为什么和你有关"。业界 AI briefing 流水线的关键一步是抽取→编辑句。

  • 对高相关条目，抓取详情页正文，用 LLM 做结构化抽取（schema 校验输出）：deadline / object（面向对象：本科生/研究生/某学院） / action_required（要不要报名/提交材料） / contact / one_line_why（一句话为什么重要）。
  • 抽取与"推理"分离（prompt 工程铁律）：deadline 只取原文明确写的，不要模型臆造；缺失填 null。
  • 抽取出的 deadline 可直接喂给现有 competition_calendar.py 的"还有 N 天"逻辑，让 DDL 块更准。

3.4 第 37 栏目（图书馆）的确定性修复

已知未决：lib.hfut.edu.cn 的 React SPA 在无头 Edge 里始终不挂载（连续两次返回 120KB noscript 兜底页），已排除代理/CDP 端口因素。这是唯一稳定失败的栏目，且对学生价值高（信息素养大赛、培训讲座）。

  • 优先排查：CDP 是否等到了 networkidle/应用挂载（目前 fetch_cdp 靠 domcontentloaded，SPA 可能还没 render 完）；尝试 wait_for_function 等待 document.querySelector('.dbTime') 出现再取 HTML。
  • 若 CDP 仍不行，改走 lib.hfut.edu.cn 的接口/SSR 数据（React 应用通常先发 JSON 数据再渲染），直接抓数据包。

3.5 AI 层成本与质量校准

  • 预过滤省钱：先用本地 Ollama/规则做"是否值得分析"的廉价判断，只有高相关条目才调云端大模型，与 changedetection 的"像素/hash 预筛→LLM 分析"成本策略一致。
  • 打分校准：relevance score 目前是关键词加权累加，可加"打分示例 + 周度人工抽检"避免阈值漂移（业界强调 calibration 比架构更重要）。
  • 本地缓存 embeddings/正文摘要，避免对未变内容重复调用模型。

3.6 可观测性 & 自愈

  • 已有 failed_channels 与 send_log.jsonl，建议加一个轻量健康面板（本地 HTML）：各栏目近 7 天成功率、覆盖度、失败率，覆盖率跌破阈值时告警。
  • 死栏目自动重试+自愈：目前失败进 hfut_failed_sites.json 下次优先重试，但连续失败无升级通知。

四、可扩展的新功能方向

4.1 个性化订阅（强烈推荐，比赛差异化核心）

现状：30 个收件人收到完全相同的邮件。但受众差异极大——保研党只关心夏令营/推免，竞赛党只关心大赛，就业党只关心秋招。业界（MyLuckyUniverse、Rasa.io）一致结论：个性化投递显著拉高打开率与价值感。

  • 每位收件人维护兴趣标签（保研/竞赛/就业/学术/奖学金）；日报按标签生成不同子集再发送。
  • 进阶：基于历史点击/打开行为做协同过滤推荐（参赛加分项）。

4.2 实时/即时告警通道

现状仅每日 08:00 批处理。对时效性极强的信息（夏令营系统开放、报名今晚截止、突发的保研政策），日报节奏太慢。

  • 新增即时告警：扫描命中"高优先级 + 新鲜度极高 + 含 deadline 临近"的条目时，立即经 apprise 推钉钉/企业微信/WxPusher/Telegram（手机推送打开率远高于邮件）。
  • 与现有每日情报互补不替代：即时通道管"此刻要行动"，日报管"今日概览"。

4.3 把 apprise 接入情报主链路

hfut_notify.py 已封装 200+ 渠道但没接到每日情报发送。把 send_daily_intel.py 的 SMTP 投递换成"SMTP 为主 + apprise 为辅"的并行投递，立刻解锁微信/钉钉/飞书订阅，受众面翻倍。

4.4 RSS / API 对外暴露

系统本身已成为最全的合工大通知聚合源。可对外提供 RSS/Atom 或 REST API，让其他人/其他系统订阅——这本身就是产品化与商业化的入口（参考 link.sc 的 aggregator 架构：canonical_url + sources + category + summary）。

4.5 知识库 / RAG 问答激活

IMA 知识库已能同步但没用起来。可做：① 历史通知语义检索（"去年保研夏令营什么时候开始的？"）；② 基于全量索引的对话式查询；③ 给日报加"相关历史"链接，形成知识连贯性。

4.6 附件下载 + OCR 全文

项目已有 ocr_extractor.py 与成本评估文档。可自动下载通知里的 PDF/图片附件并 OCR，实现正文级全文检索，对有附件的招生简章、名单公示尤其有用。

4.7 可视化 Web 仪表盘

现状是本地 HTML 报告。可加一个轻量仪表盘：栏目覆盖趋势图、分类占比、近 30 天通知量热力图、关键词云——既是日常运维工具，也是比赛演示的"系统可视化"亮点。

4.8 多校区 / 多校扩展（泛化能力证明）

架构把栏目收敛在 CHANNELS 配置里，理论上可扩展到其他安徽高校或合肥其他单位。参赛时可作为"通用高校情报中台"的泛化论证。
